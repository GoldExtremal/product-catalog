## 🔗 Состояние в URL

```text
        ┌─────────────────────────────────┐
  ┌────▶│ URL  ?q=air&category=shoes      │
  │     └────────────────┬────────────────┘
  │                      │  parseCatalogParams → toApiQuery
  │                      ▼
  │     ┌─────────────────────────────────┐
  │     │ useCatalog                      │
  │     │ requestId++ · abort прошлого    │
  │     └────────────────┬────────────────┘
  │                      ▼
  │     ┌─────────────────────────────────┐
  │     │ LRU-кэш                         │   hit
  │     │ 30 записей · TTL 10 мин         │ ───────┐
  │     └────────────────┬────────────────┘        │
  │                      │  miss                   │
  │                      ▼                         │
  │     ┌─────────────────────────────────┐        │
  │     │ GET /api/products               │        │
  │     │ deadline 10 с · 1 повтор        │        │
  │     └────────────────┬────────────────┘        │
  │                      ▼                         │
  │     ┌─────────────────────────────────┐        │
  │     │ Сетка карточек                  │ ◀──────┘
  │     └────────────────┬────────────────┘
  │                      │
  └──────────────────────┘  pushState: поиск · фильтры · страница
```

| Параметр | Правило |
| --- | --- |
| `q` | обрезка пробелов, пустой не пишется |
| `category` | id; сохраняется, пока грузится справочник, валидность проверяет API |
| `price_min` · `price_max` | число ≥ 0 |
| `in_stock` | только `true` |
| `sort` | `price_asc` · `price_desc` · `rating` |
| `page` | целое ≥ 1, `1` не пишется · `limit` — константа 24 |

Разбор и сериализация — [`src/lib/catalogParams.js`](src/lib/catalogParams.js): фиксированный
порядок полей, мусор из ссылки сбрасывается к значениям по умолчанию. Одинаковые по смыслу
ссылки дают один ключ запроса.

## 🧩 Решения

| Что | Как |
| --- | --- |
| **Источник состояния** | только URL: `pushState` при изменении, перечитывание на `popstate`; новое состояние строится от актуального URL |
| **Запись в историю** | только завершённые изменения и только если URL реально изменился |
| **Поиск** | через 300 мс после ввода или сразу по Enter |
| **Цена** | через 500 мс, по Enter или при уходе из поля. Пока ввод не закончен, обновляется одна запись истории, а не добавляются новые. Ошибка `min > max` — после окончания ввода; URL и выдача при ней не меняются |
| **Категория, наличие, сортировка** | сразу |
| **Страница** | сбрасывается на 1 при смене поиска/фильтров; номер вне диапазона заменяется последним через `replaceState` |
| **Пагинация** | заблокирована во время загрузки — нет двойного перехода; до 600 px — «Стр. N из M» |
| **Гонки запросов** | `requestId` + `AbortController` в `useCatalog`, см. [вопрос 1](#1-что-гарантирует-что-старый-ответ-не-перетрёт-новый) |
| **Кэш** | LRU в памяти вкладки: 30 записей, TTL 10 мин; возврат к прошлой выборке — без запроса. `requestId` растёт *до* обращения к кэшу, поэтому запрос в полёте не перетрёт cache hit. Ошибки не кэшируются |
| **Таймаут и повтор** | общий deadline 10 с на всю операцию; при сетевой ошибке или 5xx — один повтор через 500 мс, отменяемый вместе с запросом; 4xx не повторяются, см. [вопрос 3](#3-сервер-отвечает-500-на-каждый-третий-запрос-что-видит-пользователь-на-телефоне) |
| **Некорректная ссылка** | `price_min > price_max` — ошибка без запроса и «Сбросить цену»; ответ 400 — «Некорректные параметры ссылки» и «Сбросить фильтры» вместо бесполезного Retry |
| **Состояния** | всегда не больше одного `state-loading`: скелетон при первой загрузке и смене страницы, индикатор над приглушённой сеткой при смене фильтров. Пустая выдача — со сбросом. Справочник категорий грузится отдельно, со своей ошибкой и повтором |
| **Мобильные фильтры** | до 600 px — нативный `<dialog>` (`showModal`: модальность, фокус и Esc из коробки). Фильтры рендерятся ровно в одном месте; брейкпоинт — одна константа, проверяется только из JS |
| **Фокус** | после смены страницы — на `results-count` (`aria-live`), после ошибки — на заголовок ошибки; прокрутка к выдаче сразу по клику |
| **Библиотеки** | без UI-кита и React Query: сетка, фильтры и запросы написаны вручную, примитивы — `src/shared/ui` |

## 🧭 Отвергнутые варианты

| Вариант | Почему нет |
| --- | --- |
| **Next.js / SSR** | один экран без SEO-требований к товарам; SSR усложнил бы Docker и Lighthouse-замер ради выигрыша только в LCP (см. [производительность](#-производительность)) |
| **Vanilla JS** | состояние выдачи, загрузки, ошибок и фильтров удобнее держать декларативно; React + Vite — минимум инфраструктуры |
| **TypeScript** | JS + JSDoc + `tsc --checkJs` даёт проверку типов без шага компиляции и `.ts`-файлов |
| **React Query / SWR** | задание проверяет именно ручную логику запросов: отмену, гонки, кэш и повтор |
| **React Router** | один маршрут; History API + `URLSearchParams` прозрачнее и покрывают Back/Forward |
| **UI-кит, Tailwind** | сетку и фильтры по заданию пишем сами; CSS Modules + design tokens достаточно |
| **Кэш в `localStorage`** | ответы меняются, а URL и так источник состояния; кэша в памяти вкладки достаточно |
| **Zod и runtime-схемы** | mock API фиксирован; лишняя зависимость не окупается |
| **Бесконечная прокрутка** | обычная пагинация проще держать в URL и проверять; бесконечная — опция «если останется время» |
| **Mermaid-схема в README** | GitHub добавляет к ней кнопки масштабирования; текстовая схема читается везде |

### 🐢 Узкое место — цепочка запросов до LCP-картинки

LCP — картинка карточки товара, и браузер узнаёт о ней последней: **HTML → JS-бандл →
`/api/products` → `<img>`**. В исходном HTML картинки нет, поэтому запрос к ней ждёт всю цепочку.

```text
                      0         200       400 мс
                      ├─────────┼─────────┼─────
HTML                  █                          2–4 мс
JS-бандл, 77 КБ gzip   ██                        24–44 мс
/api/products               ████████████████     139–440 мс
картинки — LCP                               █   464–479 мс
```

<sub>Реальное время медианного прогона без троттлинга, 1 символ ≈ 20 мс. LCP 1,7 с в таблице
выше — оценка Lighthouse с Slow 4G и CPU ×4.</sub>

| Сигнал из отчёта Lighthouse | Значение | Вывод |
| --- | --- | --- |
| LCP · resource load delay | **460 мс** | почти всё время до LCP картинка ещё не запрошена |
| LCP · time to first byte | 5 мс | сервер и nginx не тормозят |
| LCP · resource load duration | 12 мс | сама картинка загружается мгновенно |
| LCP · element render delay | 93 мс | отрисовка не узкое место |
| LCP discovery | ✗ не обнаружима в исходном HTML | подтверждает цепочку JS → API → `<img>` |
| TBT · CLS | 51 мс · 0 | главный поток почти свободен, место под картинки зарезервировано |

> [!NOTE]
> Lighthouse считает LCP-элементом картинку второй карточки, а `fetchpriority="high"` стоит у первой,
> поэтому пункт «fetchpriority=high should be applied» не выполнен. На время это почти не влияет:
> картинки первого ряда запрашиваются одновременно и загружаются за 9–15 мс.

> [!TIP]
> **Что дало бы выигрыш, но не сделано:** prerender первой страницы или SSR — картинка окажется
> в исходном HTML; `<link rel="preload">` для запроса каталога по умолчанию; более лёгкий рантайм
> (например, Preact). При LCP 1,7 с на Slow 4G это не стоило усложнения в рамках таймбокса.

## 💬 Ответы на вопросы

### 1. Что гарантирует, что старый ответ не перетрёт новый?

- 🔢 Каждый запрос получает растущий `requestId`; ответ применяется, только если его id — последний.
- ✋ Предыдущий запрос отменяется через `AbortController`. Это экономит трафик, но **не гарантия**:
  ответ мог уже стоять в очереди браузера.

**Обратный порядок ответов:** новый ответ показывается сразу, старый приходит позже и
отбрасывается — его id устарел. То же при попадании в кэш: id увеличивается до обращения
к кэшу, поэтому запрос в полёте не перетрёт выдачу из кэша.

```text
запрос #4 «кроссовки» ───────────────────────── ответ ✗ id устарел, отброшен
запрос #5 «trail»     ───────── ответ ✓ показан
```

🧪 Проверка — [`e2e/search-race.spec.js`](e2e/search-race.spec.js): задержка 50–2000 мс,
5 запросов подряд, проверки после завершения или отмены *каждого* запроса.
Если убрать и проверку `requestId`, и отмену запроса, тест падает примерно в половине прогонов.
Отдельно проверку `requestId` e2e почти не задевает: устаревший запрос обычно успевает
отмениться до ответа. Её главный случай — запрос в полёте при попадании в кэш — проверен вручную.

### 2. Что лежит в URL, а что нет? Как ведёт себя «Назад» при вводе в поиск?

| | В URL | Не в URL |
| --- | --- | --- |
| **Что** | `q`, фильтры, сортировка, страница — всё, что определяет набор и порядок товаров | недоприменённый текст поиска и цены, фокус, загрузка, справочник категорий, размер страницы |
| **Почему** | ссылка, reload, новая вкладка и «Назад»/«Вперёд» восстанавливают выдачу один в один | это состояние интерфейса: им незачем делиться, а запись каждого символа засорила бы историю |

**«Назад» при вводе:**
- ⏱️ запись в истории появляется только после паузы 300 мс или Enter — «Назад» ведёт
  к предыдущему *запросу*, а не к предыдущей букве;
- ↩️ если нажать «Назад» до срабатывания таймера, отложенный поиск отменяется, а поле
  и выдача восстанавливаются из URL.

### 3. Сервер отвечает 500 на каждый третий запрос. Что видит пользователь на телефоне?

**Обычно — ничего необычного.** Запрос с ответом 500 автоматически повторяется один раз через
500 мс, и выдача появляется чуть позже, без сообщения об ошибке.

| Как падает сервер | Экран ошибки |
| --- | --- |
| строго каждый третий запрос | почти никогда: повтор получает другой номер и проходит; упадёт, только если между попыткой и повтором успеют пройти ровно два других запроса |
| случайно, с вероятностью 1/3 (`error_rate: 0.33` в mock API) | примерно в 1 загрузке из 9 (≈ 11%): обе попытки падают с вероятностью ⅓ × ⅓ |

**Если не удался и повтор:**

| Что видно | Почему |
| --- | --- |
| блок «Не удалось загрузить товары» с кнопкой «Повторить» | понятная причина и одно действие; Retry повторяет запрос с текущими параметрами из URL |
| фильтры, поиск и URL не меняются | ошибка не должна откатывать то, что пользователь уже выбрал |
| прежняя выдача остаётся ниже, приглушённая, с подписью | на мобильной сети не теряем уже загруженное |
| фокус переходит на заголовок ошибки после смены страницы | скринридер сразу сообщает о проблеме, фокус не падает в body |

**Почему так:** временные сбои сервера не стоят внимания пользователя, а один повтор не
удваивает нагрузку при настоящей аварии. Бесконечных повторов нет — общий лимит 10 с,
дальше решение за пользователем.

## ⏳ Не сделано

- **Бесконечная прокрутка** — опциональный пункт задания; оставлена обычная пагинация.
- **Реальные устройства и другие браузеры** — e2e и проверки только в Chromium.
- **E2E на таймаут 10 с** — проверен вручную (задержка 6 с + повтор → ошибка через ~10 с),
  в автотесты не вынесен, чтобы не удлинять прогон.
- **Unit-тесты хуков** (`useCatalog`, `useCatalogParams`) — их поведение покрыто e2e на реальном API.
- **Ускорение LCP** — prerender/SSR и preload запроса каталога, см. [производительность](#-производительность).
